# ADR-003 · Chunking por frontera de artículo (1000/150)

- **Estado:** Aceptado
- **Issue vinculada:** #7 — Chunking de artículos (`chunks.jsonl`)
- **Fecha:** 2026-10-06
- **Decisor:** TL (rodrigoasis87)

## 1. Contexto

El corpus tiene 227 artículos de 10 pólizas. El retrieval (ADR-004) consume
fragmentos; sin tamaño fijo, artículos largos dominarían o artículos cortos se
diluirían en fragmentos gigantes. Además, un chunk que cruza de artículo rompe
la trazabilidad de las citas (`poliza · Art. N`).

## 2. Decisión

- **Tamaño 1000 caracteres / overlap 150**, aplicado **por artículo**: un chunk
  **nunca cruza de artículo**.
- `chunk_index` = índice **0-based dentro de cada `(poliza, documento,
  articulo)`**.
- Metadata propagada desde `articulos.jsonl`: `ramo`/`año`/`familia`/
  `documento` no se re-derivan; `canonico` → `titulo_canonico`.
- Resultado actual: **758 chunks** (50 artículos por póliza aprox. → 1–3 chunks
  por artículo), con `point_id` cubierto por ADR-002.

## 3. Alternativas evaluadas

| Opción | Por qué se descartó |
|---|---|
| Segmentar por párrafo/título | Tamaños muy dispares; el embedding funciona parejo con tamaño fijo |
| 500 / 2000 chars | 500 multiplica chunks sin beneficio medido; 2000 excede el contexto útil y encarece el re-rank |
| Chunks que cruzan artículo | Rompe la cita y el colapso por `(poliza, articulo)` de ADR-004 |

> El benchmark de chunking (`feature/chunking-benchmark`, #6) puede calibrar
> estos números sobre el Golden Set (#19); el valor 1000/150 es el punto de
> partida del MVP.

## 4. Consecuencias

- E2E determinístico: `articulos.jsonl (227) → chunks.jsonl (758)`.
- El `chunk_index` entra al `point_id` → el index build sigue idempotente
  (ADR-002).
- El colapso de retrieval por `(poliza, articulo)` (ADR-004) depende de que el
  chunk nunca cruce de artículo.
