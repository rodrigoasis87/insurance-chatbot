# ADR-006 · LLM de chat intercambiable por `LLM_PROVIDER` (default local, cloud opt-in demo)

- **Estado:** Aceptado
- **Issue vinculada:** #16 (API) / #17 (query) — extensión de demo (rama `feat/demo-rag`)
- **Fecha:** 2026-10-11
- **Decisor:** TL (rodrigoasis87)

## 1. Contexto

ADR-001 definió el LLM de chat como **Ollama local (gratuito, sin API keys)** y
descartó explícitamente proveedores cloud por privacidad/costo. En CPU-only la
generación local de `qwen3:4b-instruct` toma ~40–60 s por consulta; para el
demo-day el usuario pidió poder **demostrar ambas modalidades** en la misma
sesión (local y cloud con API key, streaming) **sin cambiar el default local**
ni tocar los embeddings. El primer token en modo cloud llega después del
embedding local (~1–3 s) + decisión; el LLM de chat era el cuello de botella.

## 2. Decisión

- El LLM de chat se elige con `LLM_PROVIDER` (default **`ollama`** · ADR-001):
  `ollama | openai | anthropic | google`. `get_llm(provider=...)` (`app/rag/llm.py`)
  puede **forzarlo por petición** (demo).
- `google` → `ChatGoogleGenerativeAI` (`langchain-google-genai`) con `GOOGLE_CHAT_MODEL`
  (default `gemini-3.5-flash-lite`), `GOOGLE_API_KEY` (`.env`), `temperature=0`
  y `max_output_tokens=1024` (tope de respuesta RAG con citas).
- **Toggle por petición (opción B):** `POST /chat` y `/chat/stream` aceptan
  `provider` opcional; la UI expone un selector (`cl.ChatSettings`) que cambia de
  LLM **en la misma sesión, sin reiniciar**. Default = env (`LLM_PROVIDER`).
- **Streaming:** `query_stream()` emite tokens en vivo y detecta `NEED_WEB` por
  **peek del primer token**: preserves el contrato ≤2 generaciones LLM de
  ADR-005 (grounded = 1 generación streamed; `NEED_WEB` → corta y regenera con
  la web = 2). `query()` no-stream se conserva (scripts y tests).
- `GET /health` reporta `provider` + `model` actuales para verificar quién
  responde durante la demo.
- **Embeddings y corpus SIEMPRE locales** (ADR-001): cambiar de modelo embebido
  obligaría a reindexar `--recreate` (dimensión distinta) y a re-medir
  `UMBRAL_SCORE` (ADR-004). Se excluye explícitamente.
- Docker: el contenedor `api` recibe las variables LLM por **interpolación
  `${VAR:-default}`** en `environment` (compose lee el `.env` local), sin exponer
  las credenciales AWS del `.env` dentro del contenedor.

## 3. Alternativas evaluadas

| Opción | Por qué se descartó |
|---|---|
| GPU / modelo local más chico | Sin GPU (CPU-only); bajando modelo se degrada la calidad de las citas |
| Embeddings cloud | Hace salir la consulta incluso en modo local; exige reindexar todo y re-medir `UMBRAL_SCORE` (ADR-003/004) |
| Mantener el modo autoalojado sin excepción | La demo queda en ~40–60 s por respuesta (sin GPU) y no muestra la velocidad |
| API keys en código/compose versionado | Van solo en `.env` (gitignored), nunca en la imagen |

## 4. Consecuencias

- **Privacidad:** en modo cloud (`google`, etc.) el texto de la consulta sale
  hacia el proveedor (matiz en `docs/narrative.md`); el **default preserva**
  "la consulta **no llega a ningún proveedor de IA de terceros**" (inferencia
  autoalojada: corre en nuestra infraestructura, on-premise o en una VPS que
  administramos). El corpus son moldes sin PII (las preguntas de la demo no
  llevan datos personales).
- **Costo:** pago por token **solo si el usuario pone su key**; el modo
  autoalojado no cuesta tokens (ADR-001).
- **Latencia demo:** ~3–8 s (cloud) vs ~40–60 s (autoalojado **sin GPU**);
  con GPU (VPS de demo, overlay `docker-compose.gpu.yml`) el modelo de 4B
  responde en el orden de 1–3 s. Métrica a registrar en el demo-day. Primer
  token llega tras el embedding autoalojado (~1–3 s en CPU, <1 s con GPU) +
  decisión.
- **Reproducibilidad:** imagen única con ambos providers; 1 rebuild inicial y
  después solo se recrea el contenedor `api` al cambiar `LLM_PROVIDER` en `.env`.
- **Contratos:** `docs/CONTRACTS.md` §3.1 (LLM intercambiable + variante
  stream) y §4 (provider opcional, `/chat/stream`, `/health`).
